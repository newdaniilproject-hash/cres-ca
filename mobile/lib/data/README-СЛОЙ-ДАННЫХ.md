## Три файла

| Файл | Отвечает за |
|---|---|
| `local_db.dart` | таблицы drift = зеркало сервера + очередь исходящих |
| `outbox_service.dart` | запись: очередь, идемпотентность, разбор ошибок |
| `sync_service.dart` | чтение: дельта с сервера в зеркало |

## Главное правило

**Экран никогда не обращается к Supabase напрямую.** Читает из drift,
пишет через `OutboxService`. Из этого следует всё остальное: офлайн
не является особым режимом, поэтому не может «сломаться незаметно» —
он и есть обычный режим работы.

## Что нужно доустановить

В `pubspec.yaml`:

```yaml
dependencies:
  drift: ^2.28.0
  drift_flutter: ^0.2.4
  sqlite3_flutter_libs: ^0.5.0
  uuid: ^4.5.0
  connectivity_plus: ^7.0.0

dev_dependencies:
  drift_dev: ^2.28.0
  build_runner: ^2.4.0
```

Версии проверить `flutter pub outdated` — они на 05.08.2026 могут быть
не последними. Затем `dart run build_runner build --delete-conflicting-outputs`
(создаст `local_db.g.dart`, без него ничего не соберётся).

## Что осталось не сделано

1. **Триггеры разбора очереди не подключены.** Сейчас `drain()` зовётся
   только после постановки в очередь. Нужно добавить: при старте
   приложения, по `connectivity_plus` при появлении сети, при возврате
   из фона. Один экземпляр `OutboxService` на приложение, не на экран.
2. **Журналы не зеркалятся.** `sync_service` тянет три таблицы склада.
   Санитарные журналы (`cleaning_entries`, `sanitation_solutions`,
   `sterilization_cycles`) писать очередь уже умеет, а читать их локально
   пока нельзя — добавить таблицы и пул по `created_at` (они
   append-only, дельта честна).
3. **Первая загрузка не отделена от дельты.** Сейчас при пустой базе
   тянется всё — для салона это сотни строк, приемлемо. Если появится
   арендатор с тысячами позиций, понадобится постраничность.
4. **Очистка отправленного.** Строки со `state = 'sent'` копятся вечно.
   Удалять старше, скажем, тридцати дней — но не раньше: это единственное
   доказательство, что действие было сделано именно тогда.
5. **`tenant_id` в запросах не указывается** — его подставляет RLS
   по токену. Это правильно и намеренно; проверить на живой сессии,
   что мастер видит только свой заклад.

## Проверка, ради которой всё это

Критерий приёмки, записанный в спецификации, звучит так и проверяется
буквально:

1. Войти, дать данным загрузиться.
2. Включить авиарежим.
3. Открыть банку, списать, отметить уборку, записать раствор — пять
   действий.
4. Убедиться, что всё видно на экранах и полоса показывает «5 записів
   чекають мережі».
5. Выключить авиарежим.
6. Через минуту: очередь пуста, в базе ровно пять записей, ни одной
   лишней, остаток сошёлся с журналом движений.

Пункт 6 — самый важный. Дубли здесь означают неверный остаток
у клиента, а пропажа записи журнала — штраф Держпродспоживслужби.
