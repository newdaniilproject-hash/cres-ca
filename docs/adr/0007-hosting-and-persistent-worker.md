# ADR 0007. Хостинг: Vercel и Supabase, постоянный процесс — только по измеренной причине

**Дата:** 2026-08-04 · **Статус:** принято

## Контекст

Требование заказчика к новому проекту сформулировано прямо: всё должно
открываться молниеносно, без ожидания. В прошлом проекте для этого, помимо
Vercel и Supabase, был заведён отдельный постоянно работающий сервис
на Railway — по объяснению автора, «для ускорения сайта и админки».

Возник вопрос, копировать ли этот набор в новый проект.

Разбор боевой базы прошлого проекта встроенным анализатором Supabase
показал три причины замедления, и ни одна из них не находится в слое
хостинга:

- политики доступа, пересчитывающие функцию авторизации на каждой строке
  выборки (предупреждение `auth_rls_initplan`);
- шесть таблиц с двумя параллельными разрешающими политиками на одно
  действие — обе выполняются на каждый запрос (`multiple_permissive_policies`);
- семнадцать внешних ключей без покрывающего индекса и одновременно около
  сорока индексов, не использованных ни разу (`unindexed_foreign_keys`,
  `unused_index`).

Дополнительно: сервер авторизации сконфигурирован жёстким лимитом
в десять подключений к базе вместо доли, поэтому увеличение мощности
инстанса не ускоряло вход в принципе.

Отдельный постоянный процесс ни одну из этих причин не устраняет.
Он может их замаскировать — если держит перед базой кэш, ответы станут
быстрее в среднем и останутся такими же медленными при каждом промахе кэша,
то есть ровно тогда, когда данные изменились и продавцу важнее всего
увидеть актуальное. Это обмен предсказуемой скорости на среднюю.

## Решение

Новый проект запускается на **Vercel + Supabase**, без третьего сервиса
приложений.

Скорость обеспечивается тем, что перечислено в `docs/PERFORMANCE.md`:
права разворачиваются в токен при выдаче и не читаются из таблиц при
проверке; политики пишутся в форме, которую Postgres вычисляет один раз
на запрос, а не на строку; индексы заводятся вместе с запросом, который
их использует; публичные страницы витрины отдаются из кэша и
пересобираются по событию изменения, а не по расписанию; действия
продавца отображаются в интерфейсе до ответа сервера.

Регулярные задачи (снятие истёкших резервов, напоминания о записях,
пересчёт рейтингов) выполняются расписанием на стороне Vercel и
`pg_cron` на стороне Supabase. Фоновая обработка событий — функциями
Supabase. Этого достаточно для всего, что описано в `docs/ROUTES.md`
на сегодня.

## Когда постоянный процесс всё-таки понадобится

Не «если станет медленно», а по конкретному признаку:

Нужен процесс, который живёт дольше одного запроса и держит соединение —
приём сообщений мессенджера, длинный опрос стороннего сервиса. Нужна
очередь задач с повторами и порядком выполнения, которую неудобно
держать в базе. Появилась операция, не укладывающаяся в лимит времени
одного запроса Vercel: массовый импорт каталога, генерация выгрузки
на десятки тысяч строк. Понадобился разделяемый кэш или ограничитель
частоты обращений между экземплярами.

В каждом из этих случаев решение фиксируется отдельным ADR с указанием
измеренной причины. «Для скорости» причиной не считается: если экран
медленный, сначала смотрим план запроса и анализатор, а не добавляем
сервис.

## Следствия

**Хорошее.** Один счёт вместо двух, одно место для переменных окружения,
одна точка отказа меньше. Проблема скорости лечится там, где она возникла,
и лечение остаётся верным при росте данных — в отличие от кэша, который
надо будет прогревать и инвалидировать.

**Плохое.** Часть задач, которые на постоянном процессе решаются привычно
и просто, придётся решать в модели «функция + расписание». Для длинных
операций это означает разбиение на шаги с сохранением прогресса, а это
дороже в разработке, чем один длинный скрипт.

**Открытое.** Точное назначение Railway в прошлом проекте у автора не
уточнено дальше формулировки «для ускорения». Если там окажется что-то
из списка признаков выше — например, приём сообщений мессенджера —
это решение пересматривается сразу, и постоянный процесс заводится
осознанно под конкретную задачу, а не по инерции.

## Отвергнутые альтернативы

**Скопировать набор сервисов прошлого проекта целиком.** Отвергнуто:
воспроизводит расходы и сложность, не воспроизводя понимания, зачем.
Причины медленной работы, которые удалось измерить, лежат в схеме
и в политиках доступа и переезжают вместе с кодом на любой хостинг.

**Собственный сервер вместо Vercel.** Дешевле по счёту, дороже по времени
владельца: обновления, сертификаты, мониторинг, раздача статики по
регионам. Для проекта, который делает один человек, это не экономия.
